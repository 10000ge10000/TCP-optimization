# v0.2.0 双端真实验证报告

验证日期：2026-07-12 至 2026-07-13（Asia/Shanghai）
结论范围：单个 OpenWrt 家庭出口与单个 Debian VPS 之间的真实 TCP 链路，不代表所有运营商、地区或时段。

## 环境与拓扑

```text
Windows 11 / OpenWrt x86_64
          │ IPv4 / IPv6
          ▼
Debian 13 VPS（测试 Agent 39218，iperf3 5218）
```

真实地址、用户名、token、密钥路径和主机标识均未写入仓库。VPS 原有 5202 iperf3 服务未被停止。

| 端点 | 系统与内核 | iperf3 | 主要 TCP 状态 |
|---|---|---|---|
| VPS | Debian 13，Linux 6.12.94 | 3.18 | BBR + fq，内存约 442 MiB |
| OpenWrt | x86_64，Linux 6.6.127 | 3.17.1 | BBR + fq_codel，内存约 7.6 GiB |
| Windows | Windows 11，PowerShell 5.1 | 固定 3.18 | 只测速和建议，不写系统 TCP 栈 |

OpenWrt 缺少 `tc`，因此 qdisc drop/backlog 实测状态应为 `unsupported`，不能伪装成数值 0。链路 RTT 约 59 ms。

## 方法

- 正式共享基线使用 P1、20 秒、相同端点和端口，IPv4/IPv6 上传下载各 5 次，共 20 次。
- 吞吐 CV 均低于 10%，未扩展到 10 次；首秒和重传异常值仍保留在统计中。
- Git `HEAD` 用于旧逻辑对照；候选版使用 5 样本中位数、离散度和写入后复测。
- 统计工具输出均值、中位数、最小/最大值、样本标准差、CV、Tukey 异常值、成功率和失败原因。配对比较工具使用固定 seed、10,000 次 bootstrap。
- 原始未脱敏日志只保存在受限临时目录；仓库仅保存脱敏代表性 fixtures。

代表性命令（地址和 token 使用占位符）：

```sh
iperf3 -4 -c <VPS_IPV4> -p 5218 -t 20 -P 1 -J
iperf3 -6 -c <VPS_IPV6> -p 5218 -t 20 -P 1 -R -J

TCP_TUNE_SAMPLE_COUNT=5 sh tcp-tune.sh --yes --no-color auto \
  --host <VPS_IPV6> --port 5218 --direction upload \
  --objective retrans --rounds 2 --rtt-ms 59

sh tcp-tune.sh --no-color advanced-diagnose \
  --host <VPS_IPV6> --port 5218 --seconds 5 \
  --machine-role endpoint --critical-direction both --protocol-class tcp
```

```powershell
.\tcp-tune.ps1 join -Peer http://<VPS>:39218 -Token $token \
  -IperfPort 5218 -Direction upload -Objective retrans \
  -Rounds 1 -NonInteractive -NoColor -Yes
```

## 高级诊断和方向验证

候选版实测：

| 测试 | 上传 | 下载 |

| P1 | 74.6 Mbps / 13,094 重传 / 首秒 245.1 Mbps | 1.20 Gbps / 70,887 重传 / 首秒 811.8 Mbps |

Windows 固定资产下载通过 SHA256 和版本校验。修复 IPv4 bind 被错误用于 IPv6 目标后，IPv4/IPv6 双向各 5 次均成功。

| 家族 | 方向 | 成功率 | 吞吐中位 | 吞吐 CV | 首秒中位 | 重传 |
|---|---|---:|---:|---:|---:|---|
| IPv4 | 上传 | 5/5 | 61.95 Mbps | 2.76% | 248.42 Mbps | iperf Windows 客户端未提供，保持 `null` |
| IPv4 | 下载 | 5/5 | 1.160 Gbps | 2.23% | 749.42 Mbps | 156,100 |
| IPv6 | 上传 | 5/5 | 61.92 Mbps | 2.71% | 234.87 Mbps | 未提供，保持 `null` |
| IPv6 | 下载 | 5/5 | 1.158 Gbps | 0.13% | 741.37 Mbps | 138,632 |

Windows 完整配对首次因 Agent 拒绝 `null` 指标而失败；协议修复为允许 `null`、继续拒绝字符串和负数后，同一命令退出码为 0，页面显示“未检测”，没有误判为 0 或达标。Windows 未修改本机 TCP 栈，因此无需回滚。

## 实测推动的代码修正

1. 提前回滚后的完成轮数改为实际轮数。
2. `unsupported`、`failed`、`unknown` 和真实 0 分离。
3. Python/jsonfilter/awk 解析统一接收端吞吐和发送端重传；不安全 fallback 显式失败。
4. Shell 和 Windows 都只在地址族匹配时使用本地 bind。
5. Windows 缺失重传不再显示绿色或参与目标比较。
6. Agent 严格校验枚举、范围和类型，同时允许 `null` 表示未知。
7. 仪表盘不再把非法方向显示为下载或把缺失指标显示为 0。
8. 高级诊断的 POSIX 全局变量污染已修复，不再显示“P1 上传 下载”。
9. iperf3 客户端纳入 session/进程身份 manifest，中断时只清理本项目子进程。

## AI 验证

公共网关真实模型选择成功并返回 `gpt-5.5`。AI 自动优化在 5 样本上传阶段因波动过大以退出码 6 停止，未执行写入；随后真实摘要诊断调用出现一次结构化响应和一次上游超时。故只能证明客户端失败关闭和结构化边界有效，不能证明 AI 调参能提升当前链路。

候选 Durable Object Worker 未部署，本报告不声称线上 Worker 已验证。

## 结论

v0.2.0 在本次环境中证明了方向解析、重复样本、目标判定、失败关闭、事务回滚、Agent 只读边界和进程清理的实际作用。它没有证明能够在该链路上稳定提高吞吐或降低重传；准确结论是：**安全判断和回滚闭环有效，链路性能提升未被证明。**

## v0.3.0 AI 闭环验证（2026-07-13）

### 验证范围

本轮加入严格 AI v2 协议、本地候选控制器、多样本/holdout、专用 Worker 端点、Windows 只读解析和离线评分器。验证分为三层，结论不得互相替代：

1. 合成离线层：60 个合成场景，其中 development 48、holdout 12。
2. 本地实现层：Shell、PowerShell、Worker 单元测试及真实 workerd 运行时。
3. 外部真实层：当前公共网关上的真实模型调用；候选 Worker staging 与真实双端写入闭环尚未完成。

### 离线与本地结果

- 参考决策在 60 个合成场景上的 schema、安全召回、动作、诊断、候选、证据和重复一致率均为 100%；故障决策集正确触发验收失败。
- 该结果只证明评分器和人工标签自洽。场景及参考答案由同一开发流程生成，不能作为真实模型准确率或链路收益证据。
- Shell AI 协议测试在 Router 返修前发现：重复 evidence/reason、schema 类型、confidence 类型、空 evidence 和生成文件不同步；两轮修复后 79/79。
- AI 控制器 mock 测试覆盖停止、保留、退化回滚和非法决策失败关闭；Worker 测试覆盖严格请求、一次修复、越权拒绝、公共限流身份、熔断半开和内部推理清洗。
- 主代理复核发现候选写入后中断时只清会话目录、没有恢复尚未提交的事务；修复后信号/异常/退出均先恢复活动快照。另增加无效候选过滤、最低候选置信度和 holdout 阶段重新采集 RTT/qdisc 护栏。
- 补测白名单已收敛为当前真正实现的 `repeat_critical`；P4、PMTU、qdisc 和 CPU 高级诊断在进入 v2 证据协议前不再虚假声明为可执行补测。
- workerd 运行时测试实际加载 Worker 和 Durable Object binding，不等同于 Cloudflare staging 部署。

| Router 报告校验 | 11/11 通过，报告门禁通过；总状态仍为 `not_accepted` |

### 公共网关真实模型结果

使用不含真实主机、凭据和网络标识的合成链路证据，对当前已部署公共兼容端点执行真实调用：

| 组别 | 次数 | 严格 v2 决策成功 | 结果 |
|---|---:|---:|---|
| 现实化场景，首次提示 | 5 | 0/5 | `message.content` 为空 |
| 加入通用 canonical example 后重测 | 5 | 0/5 | `message.content` 仍为空 |
| 单个场景给出场景专属答案示例 | 1 | 1/1 | 仅证明可复述，不计入智能准确率 |
| 使用内部 reasoning 并修复一次 | 1 | 0/1 | 有 reasoning，修复后仍无合法决策 |
| 加入唯一合法 JSON 提取后的单场景复测 | 1 | 1/1 | 首次解析成功并选择 `stop_no_change`；样本不足，不计为验收通过 |
| 独立 holdout 批量探测 | 12 | 0/12 可评分 | 请求快速返回网关错误，未形成模型决策；不计为模型准确率样本 |

因此真实模型的 schema 准确率和决策准确率没有达到验收线。候选代码增加“仅提取唯一且完整通过白名单校验的 JSON”后，单个脱敏场景可从当前公共兼容响应中解析成功，说明已修复一种推理型响应格式问题；但该逻辑尚未部署到 staging，也没有跑完独立真实 holdout，不能据一个样本推断线上准确率。

12 个 holdout 的批量探测均返回 `gateway_error`，约 3 秒即结束；这组结果证明当网关不可用时评分和失败关闭生效，但不能归因为模型判断错误，也不能计入 schema/动作准确率分母。探测工具已把 `rate_limited`、`gateway_error` 与 `invalid_model_output` 分开，防止后续报告再次混淆。

### 当前验收状态

**未通过最终验收。** 当前可证明的是：协议越权会被拒绝、AI 失败时默认不写入、回滚决定仍由本地确定性逻辑掌控。当前不能证明 AI 能稳定形成正确决策，也不能证明 AI 闭环提高了真实链路性能。

尚未完成真实验证：

- 候选 Durable Object Worker staging 部署与 60 场景真实模型评测：缺少本轮部署授权及 Cloudflare 凭据。
- OpenWrt/VPS v0.3 AI 正常、退化和 holdout 写入闭环：公共模型协议未通过，继续写入测试没有验收意义；应先修复/更换模型后执行。
- 24 小时稳定性、限流、熔断和配额观测：候选 Worker 尚未部署且观察窗口未开始。
- macOS 实机、PowerShell 7 实机：环境仍未提供。

双端前置连通性已实际检查：VPS 的免密 SSH、Linux 和 iperf3 可用；OpenWrt 需要交互式密码且当前没有安全的非交互凭据注入方式。为避免密码进入命令行、进程参数或日志，本轮没有上传候选脚本、启动远端测试进程或写入 sysctl。该项属于认证安全阻塞，不能报告为双端通过。

重新验收必须满足：真实模型在独立 holdout 场景达到既定 schema、安全、动作、诊断、证据和重复一致率门槛；随后再完成双端候选写入、独立 holdout、退化回滚、参数/文件完全恢复和 24 小时 staging 观察。任何一项失败都返回修复循环，不能发布“AI 智能调参已达标”的结论。

## v0.3.0 Cloudflare staging 返工验证（2026-07-14）

本轮已实际部署两个隔离的 staging Worker，分别固定 Sub2API 与 NVIDIA 上游；未修改生产 Worker。密钥只通过 Cloudflare Secret 注入，未写入仓库或测试产物。

### 上游 A/B

使用相同 12 条 holdout 场景直接调用两家 Chat Completions。该数据集会向模型暴露合成分类证据，因此只用于比较协议服从度，不能作为真实链路智能准确率：

| 上游 | 严格决策成功 | 动作/诊断/候选准确率 | 结论 |
|---|---:|---:|---|
| Sub2API `gpt-5.5` 路由 | 4/12 | 33.3% / 33.3% / 33.3% | 不采用 |
| NVIDIA Nemotron Super | 6/12 | 50.0% / 50.0% / 50.0% | 两者中较好，但原始模型仍未达标 |

Sub2API 实际响应模型为其内部免费路由，8/12 在一次修复后仍为非法输出。NVIDIA 原始模型在“高重传、qdisc 无压力”的真实协议场景重复 5 次：2 次上游不可用、1 次非法输出、1 次超时、1 次返回 200 但错误选择候选，安全正确率为 0/5。

### 实测推动的返工

1. Worker 上游请求增加固定 User-Agent，修复 Sub2API Cloudflare 1010 拒绝。
2. Windows 下 `wrangler secret put` 的管道换行曾导致两家上游均返回 401；改用 UTF-8 JSON `secret bulk` 后恢复。临时 Secret 文件创建于系统临时目录并立即删除。
3. NVIDIA 调参请求启用官方 `nvext.guided_json`；模型切换时熔断状态按“上游 + 模型”隔离，避免旧模型故障污染新模型。
4. 修复提示加入精确枚举、动作约束、CV 单位、qdisc 标签、BDP 与首秒比例；非法决策仍只允许一次修复且最终失败关闭。
5. Shell 发往 AI 的 qdisc 从无标签的两个数字改为 `drop=<count> backlog=<bytes>`。
6. 加入本地确定性证据层：只读平台、UDP/QUIC、零重传、既往退化回滚、qdisc 路径拥塞、BDP 和首秒起速先由本地数学/安全规则处理；AI 只处理证据冲突和非显然选择。候选写入后仍必须经过本地多样本、独立 holdout 和自动回滚。

### staging 复测

等待 Cloudflare Secret 传播并完成预热后，同一 NVIDIA staging 对 8 类协议场景全部返回 HTTP 200：只读、UDP/QUIC、健康、队列压力、补测后队列压力、BDP、快速起速、既往退化回滚为 8/8。路径拥塞护栏随后独立重复 5 次，5/5 均返回 `stop_no_change + path_congestion`，没有选择任何候选。

该结果证明“混合控制器的 staging 决策边界”达到当前场景验收，不证明原始大模型准确，也不证明真实链路性能提升。生产 Worker 未部署；OpenWrt/VPS 的 v0.3 实际候选写入、复测、holdout 与回滚仍需继续完成，24 小时稳定性观察也尚未开始。

## v0.3.0 OpenWrt/VPS 最终闭环补测（2026-07-14）

本节覆盖上一节尚未完成的真实双端项目，并以本节结论为准。测试仍使用隔离端口、状态目录和脱敏地址；没有修改防火墙、DNS、DHCP、WAN、代理、路由或 forwarding。VPS 原有 5202 iperf3 在全部测试后仍由原 PID 监听。

### 同条件 5×20 秒基线

IPv6、P1 单线程、`-O 0`、上传/下载各 5 次，异常值不删除：

| 方向 | 成功率 | 平均 | 中位 | 最低–最高 | 样本标准差 | CV | 重传中位（范围） |
|---|---:|---:|---:|---:|---:|---:|---:|
| 上传 | 5/5 | 64.15 Mbps | 64.33 Mbps | 63.65–64.48 | 0.34 Mbps | 0.53% | 17,107（17,051–18,669） |
| 下载 | 5/5 | 1062.04 Mbps | 1170.15 Mbps | 765.50–1192.53 | 182.77 Mbps | 17.21% | 118,109（73,229–200,966） |

下载吞吐 CV 达 17.21%，因此不具备直接比较小幅参数收益的条件。上传吞吐稳定，但重传持续较高。

### AI 真实流程与迭代

1. 首次 AI 闭环被旧稳定性门禁拦截：实现错误地要求吞吐、重传、首秒三个 CV 同时不超过 10%。修正为仅吞吐触发扩样，重传/首秒 CV 进入目标判定；候选保留新增目标指标 CV 不超过 20% 的硬护栏。
2. 一次验证配置漏写 `/v1` 返回 404，该结果属于测试配置错误，不计入模型验收。
3. NVIDIA 单上游真实调用返回 502。加入 NVIDIA 优先、Sub2API 对可重试故障兜底后，证据冲突场景仍有 4/5 非法模型输出、1/5 超时，证明原始模型路径未达标。
4. 实机确认 OpenWrt 没有 `tc`，IPv6 原生路由返回不可达但连接由现有代理路径承载。代码改为 qdisc 缺依赖优先报告 `unsupported`；高重传且 qdisc 证据不可用时，本地安全层停止候选写入。staging 重复 5/5 返回 `stop_no_change + unstable_evidence`。
5. 同一真实双端再执行上传/下载各 5×20 秒后，AI 决策为 `stop_no_change`，候选实验 0、holdout 0，退出码 0；没有写入 sysctl，也没有虚构优化收益。

### 写入、退化与回滚闭环

为验证事务本身，另运行重传优先两轮稳定优化。第一轮 3 样本中位数为 62.3 Mbps / 13,691 重传；白名单候选写入后第二轮为 62.2 Mbps / 14,380 重传，重传上升约 5%。本地目标判定拒绝候选并自动回滚。随后显式执行 `rollback` 再次成功。

恢复核对：

- `/etc/sysctl.d/99-tcp-tune.conf` SHA256 恢复为测试前值。
- OpenWrt 最小配置文件 SHA256 与备份原文一致。
- `tcp_mtu_probing=1`、`tcp_slow_start_after_idle=0`、`tcp_notsent_lowat=262144`、`tcp_limit_output_bytes=262144` 全部恢复。
- qdisc 为 `unsupported` 时没有绕过护栏或伪造 0。

### Agent 真实异常与清理

无 token/错 token/header/query 分别为 403/403/200/403；非法 JSON、任意 restore 字段和超限 body 分别为 400/400/413。真实测试同时发现下载脚本没有 executable bit 时 `/status`/`restore-defaults` 会触发 `PermissionError`；Agent 已统一通过 `/bin/sh` 调用固定脚本，并捕获启动异常。复测 `/report`、`/status`、`/events`、显式 allowlist `/test`、固定 `/restore-defaults` 全部为 200。

同端口重复启动退出码 4。3 秒 TTL 后 39218/5218、token、PID、manifest、临时 Python 和锁均消失；仅保留无敏感信息的日志与初始快照供审计。伪造 manifest 指向独立 `sleep` 时进程保持存活并明确报告身份不符。项目原有 5202 iperf3 未被停止。

### 当前结论

真实双端证明了 AI 能在证据不足时安全停止、事务写入后能以复测结果自动回滚、手动回滚能完整恢复文件和运行值。它仍没有证明此链路获得稳定性能提升；准确结论仍是：**安全决策和回滚闭环通过，性能提升未证明。** 原始模型准确率、生产 Worker、24 小时稳定性、macOS 实机和 PowerShell 7 实机仍未通过最终验收。
